### What was built
- **Central state machines** — `AttemptStateMachine` (`PostPublicationAttempt.status`: `pending→processing→success|retry_scheduled|failed`, `failed→dead_letter`, `dead_letter→pending` for manual retry) and `PostStateMachine` (wires the previously-dead `config('publishing.allowed_status_transitions')` into real enforcement). Every status change in the publishing pipeline now goes through one of these two — no more scattered raw `->update(['status' => ...])`.
- **Atomic claim, not read-then-write**: `AttemptStateMachine::claim()`/`claimDueRetry()`/`reclaimStale()` are all conditional `UPDATE ... WHERE status = X AND claimed_at IS NULL`-style calls with an affected-rows check, so two workers racing for the same attempt can never both proceed.
- **Idempotency**: `PublishEngineService::idempotencyKey()` hashes `organization_id + post_id + social_page_id + publish_batch_key` (the "publication_intent" — a fresh batch key is generated on every genuine new schedule/publish-now request, so an intentional re-publish is never blocked, but a resend of the same request always resolves to the same row). DB unique constraint already existed on `idempotency_key`; `findOrCreateAttempt()` catches the race on that constraint and hands back whichever row actually landed.
- **Error classification + retry**: `PublishErrorClassifier` sorts every failure into `retryable`/`non_retryable`/`unknown` from real HTTP status codes (required replacing bare `RuntimeException` throws in `FacebookOAuthProvider`/`TelegramProvider` with a new `ProviderPublishException` carrying `httpStatus`/`retryAfterSeconds`/`responseBody`). `RetryBackoffCalculator` does exponential backoff with ±30% jitter; a provider's own `Retry-After`/Telegram's `parameters.retry_after` is honored over the calculated backoff when present.
- **Two-tier circuit breaker**: `PublishEngineService` now tracks failure counters/circuit-open flags per provider (shared, high threshold — genuine platform outages) AND per organization+provider (low threshold — one tenant's revoked token trips only that tenant's breaker). Verified an org-tripped breaker never affects a different organization publishing to the same provider.
- **Dead-letter queue**: `PublishEngineService::pushToDeadLetter()` (scalar-only payload — explicitly never the raw provider request/response, so a leaked DLQ row can't leak a credential) + a new permission-gated, audited manual retry endpoint (`POST /publishing/dead-letters/{deadLetterJob}/retry`, `publishing.manage`). The retry re-opens and re-processes the **same** attempt row (same `idempotency_key`) rather than creating a new one — the DLQ row's own `retried_at IS NULL` claim is itself a conditional-UPDATE-with-affected-rows-check, so two admins clicking retry simultaneously still only ever dispatch one retry job.
- **`dead_letter_jobs.organization_id`** — this table had **no organization_id at all**, discovered mid-sprint while building the retry endpoint: `PublishingController::deadLetters()` was listing every organization's dead letters to anyone holding the (global, non-org-scoped) `publishing.monitor` permission. Fixed: new migration backfills from the referenced attempt/post, locks NOT NULL, adds `BelongsToOrganization` to the model — the existing listing endpoint is now automatically tenant-scoped via the trait's global scope, and the retry endpoint 404s on another organization's dead letter via route-model binding, before any handler code runs.
- **`RetryDuePublishAttemptsJob`** — scheduled every-minute sweeper (`routes/console.php`) that re-dispatches `PublishPostJob` for due `retry_scheduled` attempts; does no claiming itself, so a sweeper run racing a still-live worker just no-ops on the loser side via the same atomic claim.
- **Two real bugs found and fixed while writing the mandatory acceptance tests** (not assumed away):
  1. **Cancelled posts could still be published.** `PublishPostJob::handle()` had no check that the post was still in the `publishing` state it started in — a user calling `markDraft()` to cancel a post *after* its job was already queued (but before a worker picked it up) had no effect; the job would publish it anyway. Fixed with an explicit `if ($post->status !== 'publishing') return;` guard. `RetryDeadLetteredAttemptJob` got the equivalent guard (`status !== 'failed'` → no-op).
  2. **A crashed worker's stale claim was blindly retried against the provider a second time.** `reclaimStale()` only ever reset `claimed_at`/`claimed_by`, and the caller then proceeded straight to `callProvider()` again — meaning "worker crashes after Facebook/Telegram already accepted the post, before the DB row updates" would cause a genuine duplicate publish on reclaim. Neither provider's public API accepts a client idempotency token, so there's no way to safely check "did that in-flight call already succeed?" before retrying. Fixed: a reclaimed stale attempt now finalizes immediately as `ambiguous_after_crash` (new `PublishErrorClassifier` constant) straight to the DLQ — never re-calls the provider — so a human can verify the actual page/channel before using the manual DLQ retry. This is the one criterion (#3) where "never publish twice" and "never silently lost" are in real tension for these providers; the resolution favors never-duplicate, with the DLQ + manual retry as the "not silently lost" half.
  - **Dead config found and fixed in the same pass**: `config('publishing.backoff_base_seconds'/'backoff_max_seconds')` was defined but never actually read — `PublishEngineService` constructed `RetryBackoffCalculator` with a hardcoded default via constructor promotion, so changing the env vars would have silently done nothing. Fixed by building the calculator from config in the constructor body (a promoted-property default can't call `config()` — it must be a compile-time constant).

## Sprint 5 (SaaS Business) — SCHEMA STARTED, 2026-07-29 (no pricing decided yet, by design)

Deliberately just the plumbing: `plans`, `organization_subscriptions`, `billing_webhook_events` tables + models + one wired checkpoint. No price is seeded anywhere — this project has repeatedly found fabricated-looking data presented as real elsewhere in this audit (fake dashboard stats, aspirational docs); seeding a plausible "$9/mo Starter" row would be the identical mistake with pricing. Real plans get created once the user provides real pricing/tier decisions.

- **`plans`** (`name`, `slug`, nullable `price_cents`/`billing_interval`/`currency`, `limits` JSON, `is_active`). Limits are a JSON map (e.g. `max_team_members`) rather than dedicated columns, so new limit types don't need a migration each time. A missing key means unlimited.
- **`organization_subscriptions`** — one row per organization (`organization_id` unique), `plan_id` nullable, `status` (trialing/active/past_due/canceled), period/trial timestamps, a `provider_subscription_id` placeholder for whichever payment provider gets chosen later. **This table starts empty** — every organization that exists today has no row here.
- **`billing_webhook_events`** — idempotency store for whatever payment-provider webhook eventually arrives (`unique(provider, provider_event_id)`), same "atomic claim, not read-then-write" principle as Sprint 3's publishing pipeline. No provider-specific signature-verification code yet — no provider has been chosen.
- **`OrganizationEntitlements`** (`app/Support/Billing/`) — the one place application code should ever ask "can this organization do X more of this." An organization with no subscription row, an inactive one, or a plan with no limit set for a key is always **unlimited**, never zero — the only backward-compatible default, since this table starts empty for every existing organization.
- **One concrete checkpoint wired**: `OrganizationMembershipController::store()` (team invites) now checks `max_team_members` before creating a new membership. A no-op for every organization today (no subscription rows exist), real once a plan with that limit is actually assigned. 4 new tests: unlimited-by-default, limit enforced once a subscription+plan exist, the invite endpoint actually rejects at the limit, and the invite endpoint still works normally with no subscription (regression guard against breaking every existing organization).
- **Real bug caught by Larastan while building this**: `Plan`'s usage-limit lookup was originally named `limit(string $key)` — collides with Eloquent's own `Model::limit(int $value)` (the SQL LIMIT clause, forwarded via `__call`). It happened to still work correctly at runtime (PHP resolves the model's own declared method before falling through to `__call`), but PHPStan/Larastan couldn't verify it at all and flagged a real type mismatch — renamed to `usageLimit()` to remove the collision entirely rather than leaving a landmine for the next person who calls `$plan->limit(...)` expecting the ubiquitous Eloquent meaning.
